## 1. Архитектура в двух словах

```
PWA (телефон)  ──GET ?action=…──►  doGet   ──►  таблица «Бар — журнал» (чтение)
               ──POST {action}──►  doPost  ──►  LockService ──►  запись строк
                                                      │
                                              Drive (фото уборки, фото ТТК)
                                              Gemini API (проверка фото — не включена)
```

* Один проект, один файл, ~900 строк, без фреймворков и без внешней БД — таблица и есть БД.
* Скрипт запускается **от имени владельца** (`executeAs: USER_DEPLOYING`), доступ — **«Все»**
  (`access: ANYONE_ANONYMOUS`), то есть URL доступен кому угодно без авторизации Google.
* Авторизация — только внутренняя: имя сотрудника + PIN, приходящие в каждом запросе/записи.
* Запись — через очередь на телефоне (IndexedDB) и пачки до 50 записей за POST.
* Чтение — конфиг целиком (сотрудники, справочник позиций, причины, зоны, ТТК, опись,
  шаблоны актов), по одному фото ТТК в base64, список «актов в работе».
* Есть расписание для ИИ-проверки фото уборки (Gemini) и автоудаления — но **не настроено**
  (0 триггеров, нет свойства `GEMINI_API_KEY`), подробности в §8.

Важные свойства схемы:

* **Первая строка — заголовки**, данные с 2-й (`rows_()` `:671` читает со 2-й строки).

* Два листа — «Свод переработки» и «Итог инвентаризации» — код не читает и не пишет,

* «Итог инвентаризации» в шапке показывает период («Инвентаризация:» / «Октябрь»),

## 4. Авторизация, роли, PIN

### Как устроено

* PIN лежит **в открытом виде** в листе «Сотрудники», колонка B («PIN (4–6 цифр)»).
  Хеширования нет, сравнение — строка со строкой: `if (str_(row[1]) !== pin)` (`Код.gs:253`).
* `checkPin_()` (`:238`) — единственная проверка. Вызывается из `login_()` (`:227`) и
  **на каждую запись** из `submit_()` (`:301-303`), с мемоизацией в пределах запроса
  (`authMemo`, `:281`), чтобы не проверять PIN 20 раз за пачку.
* Сотрудник должен быть активен: `row[3] !== true` → «Сотрудник не найден или отключён»
  (`:252`).
* Роль — колонка C, отдаётся клиенту как есть (`:257`), по умолчанию `бармен`.
* PIN на телефон не уходит в `config` (`:105-108` — только имена активных), но
  **уходит в каждом запросе записи**: фронт хранит его в памяти сессии
  (`js/app.js:227`) и кладёт в каждую запись очереди (`js/sync.js:57`, `js/app.js:467`,
  `1024`, `1143`), то есть он лежит и в IndexedDB на телефоне, пока запись не отправлена.

### Ограничение попыток входа

* `PIN_FAIL_LIMIT = 8`, `PIN_FAIL_WINDOW_SEC = 15 мин` (`Код.gs:61-62`).
* Счётчик — `CacheService.getScriptCache()` по ключу `pinfail:<имя>` (`:243-248`).
* 8 неверных PIN по имени → `{ok:false, error:'Слишком много неверных PIN. Подождите 15 минут.', code:'locked'}`
  (`:246-248`). Успешный вход счётчик **не сбрасывает** (мелочь, но неприятная:
  можно «дозакрыть» себя, набрав ошибки до верного ввода).
* Кэш скрипта общий на всех и может быть вытеснен Google в любой момент — тогда счётчик
  обнулится. Жёсткой защиты от перебора нет: 4-значный PIN при лимите 8 попыток / 15 мин
  на имя перебирается примерно за 13 суток непрерывной работы, 6-значный — за ~3.5 года.
  Но лимит **на имя**, а не на IP; имена публичны (см. ниже).
* `checkPin_` различает «Сотрудник не найден или отключён» (`code:'auth'`) и «Неверный PIN»
  — это позволяет перечислять имена, если бы они не были и так открыты.

### Роли — только на клиенте (кроме одной проверки)

| Роль | Что реально проверяет сервер | Что проверяет фронт |
|---|---|---|
| `бармен` | ничего | скрывает разделы (нет) |
| `менеджер` (`/^менедж/`) | **ничего** | показывает Gift-shop |
| `админ` (`/^админ/i`) | только в `submit_` (`:309-320`): разрешены `transfer`, `writeoff`, `inventory`; инвентаризация — только места Gift-shop и категория Gift-shop / «Нет в описи» | то же (`js/app.js:249-256`) |

То есть, зная свой PIN, **бармен может отправить в API любую запись любого типа**
(включая инвентаризацию любого места и любой акт) — сервер её примет. Роли на сервере
декоративные, кроме ограничения «админ». Названия ролей — произвольный текст в колонке C,
сравнение идёт по первым буквам (`startsWith`/регулярка), так что «Администратор» сработает,
а « admin» — нет.

### Что видит клиент

* Без PIN можно получить: имена всех активных сотрудников, весь справочник позиций,
  причины списаний, зоны уборки, все ТТК (рецепты, заметки) и **все фото ТТК**
  (id файлов приходят в `config`, а `ttkPhoto` отдаёт файл по любому id из листа ТТК).
  Это не «утечка доступа», это дизайн — но фактически внутренние рецептуры и фотографии
  открыты любому, кто знает URL веб-приложения.
* `openActs` без PIN отдаёт, какие акты сейчас «в работе», кто их начал и ожидаемый выход.
* PIN нигде не отдаётся клиенту, но передаётся в открытом виде (по HTTPS) в каждом запросе.

## 5. Идемпотентность и блокировки

### Идемпотентность по ID записи

* ID придумывает телефон (`js/sync.js:50-54`, UUID v4) и кладёт в запись.
* На сервере: формат проверяется регуляркой `/^[A-Za-z0-9-]{8,64}$/` (`:299`), иначе
  `status:'error'`, `error:'Некорректный ID записи'` — **без `retry`**, фронт пометит запись
  «отклонено».
* Дубль: `idExists_(sheet, col, id)` (`:330`) — `createTextFinder(id).matchEntireCell(true)`
  по столбцу ID нужного листа (`:620-625`). Найден → `{id, status:'duplicate'}` **без записи**.
* Поиск идёт по конкретному листу и колонке (`ID_COLUMN`, `:47-54`), поэтому ID уникален
  в пределах листа, а не глобально. Разные типы записей с одинаковым ID не конфликтуют.
* Если строку с ID удалить руками — та же запись от телефона пройдёт ещё раз.

### Блокировка

* `LockService.getScriptLock()` + `tryLock(30000)` (`:275-276`) — на **всю** обработку
  пачки: чтение справочника сотрудников, все записи, `SpreadsheetApp.flush()` (`:290`),
  затем `releaseLock()` в `finally` (`:293`).
* Не дождались блокировки за 30 с → `{ok:false, error:'Таблица занята, повторите позже'}`
  (это `ok:false` без `code`), фронт считает это `ApiError`, оставляет записи в очереди и
  повторит позже (`js/sync.js:129-133`).
* Внутри блокировки всё последовательно, поэтому гонок «прочитал ID → не нашёл → записал»
  между двумя запросами нет.
* Блокировка **скриптовая**, то есть одна на всё веб-приложение: пока один телефон
  заливает фото на 6 МБ (до 90 с таймаута на клиенте), остальные ждут. Очередь запросов
  Apps Script к тому же сама по себе может ждать, а лимит времени выполнения — 6 минут
  на запрос (`submit_` может обработать до 50 записей и на каждой читать/сканировать лист).
* Опасный побочный эффект: `addRow_()` (`:606`) на каждую запись читает **весь столбец A**
  листа (`getRange(1,1,getMaxRows(),1).getValues()`), а `saveInventory_()` — диапазон
  2…N×13 (`:452`). На листах в тысячи строк пачка из 50 записей легко упирается в лимиты.

### Отдельно про акты переработки

* Акт приходит одной записью: строка на каждое сырьё + строка «Результат», у всех общий
  `ID акта` в колонке K.
* «Выход запишу позже» (`pending`, `:503-506`): строка результата пишется с пустым «Кол-во»
  и статусом `⏳ В работе`.
* Закрытие — отдельная запись `processingClose` (`:529`) с **другим** ID, который хранится
  в колонке P «ID закрытия»; она находит строку результата по ID акта и дописывает её.
  Если акт ещё не доехал (лежит в очереди другого телефона) → `{status:'error', error:'Акт пока не найден в таблице', retry:true}`,
  и телефон повторит (`js/sync.js:12-13`). Закрыть может любой бармен — так задумано;
  повторное закрытие отбивается проверкой статуса (`:539-541`).

## 6. Ошибки, коды и `retry`

### Формат ответа

* Успех POST: `{ok:true, results:[…]}`. Даже если отдельные записи не сохранились —
  `ok` всё равно `true`; судить надо по `results`.
* Верхнеуровневый отказ: `{ok:false, error, code?}` (нет записей / слишком много / нет блокировки).
* GET: либо полезные данные с `ok:true`, либо `{ok:false, error}` — **без `code`**.

### Статусы записей и флаги

| Статус | Когда | `retry` | Действие фронта (`js/sync.js:141-149`) |
|---|---|---|---|
| `saved` | записано | — | убрать из очереди, положить в «Отправленные» |
| `duplicate` | ID уже есть в листе | — | то же |
| `error` + `retry:true` | исключение при записи (`:287`) | да | оставить в очереди |
| `error` + `code:'locked'` | PIN-лимит исчерпан (`:247`) | нет | оставить в очереди (код проверяется явно) |
| `error` + `code:'auth'` | нет сотрудника / неверный PIN | нет | пометить «отклонено» |
| `error` без `retry`/`code` | невалидные данные, нет листа, нет шаблона и т.п. | нет | пометить «отклонено», показать причину |

Записи `processing`, «закрытие ещё не доехало» — тоже `retry:true` (`:537`).

## 7. Соответствие контракту фронтенда

Контракт из `js/api.js` и `js/sync.js` реализован, расхождений по «жизненно важным» пунктам нет.

| Фронт ждёт | Сервер | Статус |
|---|---|---|
| GET `?action=config` | `:73` | ✅ |
| GET `?action=ttkPhoto&id=…` → `{ok, mime, data}` | `:74`, `:208` | ✅ |
| GET `?action=openActs` → `{ok, acts}` | `:75` | ✅ |
| POST `{action:'login', name, pin}` → `{ok, name, role}` | `:88` | ✅ |
| POST `{action:'submit', records:[…]}` → `{ok, results}` | `:89` | ✅ |
| `results[].status` = `saved` / `duplicate` / `error` | `:350-386` | ✅ |
| `results[].retry` | только исключения и «акт не найден» | ✅ (но редко) |
| `results[].code === 'locked'` для «повторить позже» | `:247` | ✅ |
| `ok:false` → `{error, code}` | `code` есть только у PIN-ошибок | ⚠️ `code` часто отсутствует |
| `Content-Type: text/plain` без preflight | сервер не ставит CORS-заголовки, но и не требует | ✅ |
| Идемпотентность по UUID телефона | `:330` | ✅ |
| Pin не приходит в `config` | `:105-108` | ✅ |

Что есть на сервере, но фронт не использует:

* `action=ping` — готовый health-check, в приложении не вызывается;
* поле `fileId` в ответе на фото (`:385`) и `total` в ответе инвентаризации (`:472`);
* поля `config.theme`, `config.units`, `config.directions` — **используются** (`js/app.js:125, 412, 514`).

Что фронт делал бы иначе / мелкие несостыковки:

1. **`config` не требует PIN, хотя PIN есть в системе.** Любой человек с URL получает
   весь ТТК и фото. Если это не задумано — это первое, что надо закрывать.
2. **`code` в ошибках почти всегда пустой.** `js/api.js:37` создаёт `ApiError` с `code`,
   но сервер присылает его только для `auth`/`locked`. Фронт живёт, но диагностика хуже.
3. **`openActs` отдаёт `basis` точнее, чем фронт:** `js/app.js:346` для локально
   посчитанных ожиданий всегда пишет `'по рецепту'`, сервер для простых актов пишет
   «средний выход прошлых актов N%» (`:589`).
4. **`status:'rejected'` — клиентское понятие.** Сервер про него не знает; «окончательный
   отказ» — это `error` без `retry`/`locked`. Это соответствует, но в базе сервера
   никакого следа отказа нет: если телефон потеряется, никто не узнает, что запись не дошла.
5. **Комментарий в `js/app.js:811`** ссылается на лист «Нет в описи», которого в таблице
   нет: фактически позиции вне описи помечаются в «Подсчёте» категорией `Нет в описи`
   и комментарием `⚠ Нет в первичной описи` (`Код.gs:413, 462-466`). Это старый комментарий.
6. **Лимит пачки 20 (фронт) против 50 (сервер)** — не конфликт, просто сервер терпимее.
7. **Таймаут фото на клиенте 90 с** при лимите выполнения Apps Script 6 минут — ок,
   но при 6-МБ фото и занятой блокировке 30 с ожидания реально получить «Таблица занята».

## 9. Риски и слабые места (по приоритету)

### P0 — открытый endpoint без реальной аутентификации

`appsscript.json`: `access: ANYONE_ANONYMOUS`, `executeAs: USER_DEPLOYING`. Значит:

* URL работает у кого угодно, без входа в Google; владелец при этом платит квотами и
  даёт доступ к своему Диску и таблице;
* без всякого PIN отдаётся: список активных сотрудников, весь справочник, все ТТК и
  **все фото ТТК**, список актов в работе;
* запись защищена только PIN из 4–6 цифр, который сотрудник вводит с телефона;
* любой, кто получил URL (а он лежит в открытом `config.js` на GitHub Pages —
  `https://sangoskarlet.github.io/bar-app/`), может писать записи, зная чей-то PIN;
* при этом `SPREADSHEET_ID` в коде — не секрет, а таблица, скорее всего, доступна
  по ссылке в организации.

Что делать: закрыть `config`/`ttkPhoto`/`openActs` хотя бы сессионным токеном, выдаваемым
`login`, и хранить его в `PropertiesService`/кэше; либо перевести веб-приложение на
`access: ANYONE` + Google-аккаунты; минимум — убрать `photoId` из публичного `config`
и отдавать фото только после логина.

### P0 — PIN в открытом виде + PIN в каждом запросе

PIN хранится открытым текстом в таблице (колонка B «Сотрудники»), сравнивается строкой,
и уезжает на сервер в каждой записи. Кто имеет доступ к таблице (а её смотрит весь бар),
видит все PIN. Рекомендация: хранить хеш (например, `Utilities.computeDigest`) или
перейти на одноразовые токены; PIN — 6 цифр минимум, не 4.

### P1 — перебор PIN и отсутствие общей защиты от флуда

Лимит 8/15 мин на имя в `CacheService`: кэш может вытесняться, счётчик не сбрасывается
после успешного входа, лимита на IP/устройство нет. Плюс нет ограничения на `GET config`
— его можно дёргать сколько угодно (и каждый вызов читает всю таблицу: ~1000 строк «Описи»,
300 «ТТК» — дорого по квотам).

### P1 — квоты Apps Script

* **6 минут на выполнение** веб-приложения: `submit_` на 50 записей, где каждая читает
  лист и `addRow_` сканирует весь столбец A, реально может не уложиться на больших листах.
  Тогда клиент получит `Ошибка сервера` (запись уже частично записана — но идемпотентность
  по ID спасает от дублей, а клиент повторит).
* **20 000 `UrlFetchApp` в сутки** — сейчас расходуется только Gemini (не включён).
* **Триггеры**: 90 мин/сутки на аккаунт (потребительский) — при включении `checkPhotos`
  раз в 10 минут это ~144 запуска; каждый запуск читает лист и делает до 8 запросов к Gemini.
* **`CacheService`**: TTL максимум 6 часов, значение до 100 КБ — на счётчике PIN не критично.
* **`LockService`**: ожидание 30 с внутри 6-минутного лимита — если фото льётся долго,
  остальные запросы падают с «Таблица занята».

### P1 — деплой: версия на `/exec` может отставать

Факты на 17.11.2026:

* на `/exec` активно развёртывание с ID `AKfycbz…N7-w`, **Версия 9 от 15.11.2026 03:01**,
  доступ «Все», запуск «от моего имени (sangoskarlet@gmail.com)»;
* в «Истории проекта»: Текущая версия (15.11 03:00), Версия 9 (15.11 03:01), Версия 8
  (14.11 21:10), 7 (12.11 17:36), 6 (12.11 17:03), 5 (12.11 17:00), 4 (12.11 15:48),
  3 (12.11 14:03), 2 (12.11 13:05), 1 (12.11 13:00) — то есть v9 и есть последняя
  нумерованная версия, разрыв маловероятен;
* живой `?action=ping` ответил `{ok:true,…}` — значит на `/exec` крутится именно этот код;
* **в архиве 8 старых развёртываний** («Без названия» ×8) — если у кого-то сохранился
  старый URL, он может писать в ту же таблицу старым кодом.

Чем это опасно на будущее: правка в редакторе **не меняет** опубликованный URL, пока не
сделано «Развернуть» (сама страница настроек проекта это и пишет: «Внесенные в них
изменения не повлияют на существующее развертывание»). У проекта нет ни CI, ни `clasp`,
ни тестов — «доехало или нет» проверяется только руками. Это классическая поломка:
поправили код, забыли переразвернуть (или наоборот развернули не тот).

Рекомендация: держать исходники в git (этот каталог), подключить `clasp`/`@google/clasp`
или Apps Script API, и после каждого деплоя делать `?action=ping` + одну запись-«канарейку».

### P2 — нет истории версий и бэкапов (в смысле восстановления)

* У кода история есть: 9 версий проекта + архив развёртываний (Apps Script хранит их сам).
* У **данных** отдельного бэкапа нет: только штатная история изменений Google Таблиц
  (она есть, но её легко не заметить и она не заменяет выгрузку). Если лист случайно
  очистят или формула сломает данные — восстанавливать придётся через «Файл → История
  версий».
* Автоматического экспорта (xlsx/CSV в Drive по расписанию) нет.
* Кода вне Google не было вообще до этой выгрузки — теперь есть в git.

### P2 — переполнение листов

* `addRow_()` (`:606-617`) считает последнюю заполненную строку по столбцу A и при
  необходимости добавляет 50 строк (`insertRowsAfter`). Верхнего предела нет.
* Google Таблицы: 10 млн ячеек на книгу. «Опись» уже ~1000 строк × 10 колонок,
  «ТТК» — ~300 × 9; журналы растут. При 10 млн ячеек `insertRowsAfter` начнёт падать,
  и все записи пойдут в `error` + `retry:true` — то есть будут вечно висеть в очереди
  у барменов.
* Отдельно «Лог»: `log_()` (`:714-721`) сам себя подрезает — при >2200 строк удаляет
  200 старых. При этом `deleteRows(2,200)` сдвигает строки и **удаляет историю ошибок**;
  если ошибка происходит часто, лог будет «крутиться» и старые причины исчезнут.
* Плохой симптом: `addRow_` не умеет отличать «пустая строка с форматированием» от
  данных и сканирует **всю** сетку (`getMaxRows()`), а не `getLastRow()` — на больших
  листах это лишние секунды на каждую запись.

### P2 — роли и права

* Сервер не ограничивает бармена: любой тип записи, любое место инвентаризации.
* Экран «Итог инвентаризации» и «Свод переработки» — формулы в таблице, их может
  править любой, у кого есть доступ к таблице.
* Нет журнала «кто что читал»: лист «Лог» пишет только ошибки и служебные события.

### P3 — прочее

* **Нет CORS-заголовков** (Apps Script их не умеет). Работает только потому, что фронт
  шлёт `Content-Type: text/plain` и не вызывает preflight (`js/api.js:52-57`). Любая
  попытка отправить `application/json` или добавить кастомный заголовок сломает запросы.
* **Ошибка в `saveOne_` для фото:** файл на Диске создаётся до записи строки (`:375`);
  если `addRow_` упадёт, останется «сирота» — файл без строки в таблице.
* **`photoFolderFor_` хранит `PHOTO_FOLDER_ID` в свойствах скрипта** (`:635-641`): если
  папку удалить, скрипт создаст новую — и старые фото окажутся в «потерянной» папке.
* `parseDate_()` (`:696-703`) отбрасывает времена «из будущего > 24 ч» и «старше 60 дней»,
  подставляя время сервера — при долгой офлайн-очереди запись «переедет» на дату отправки.
* `text_()` ставит апостроф: при экспорте в CSV/Sheets API в значениях может появиться
  ведущий `'`, что сломает сравнения в сторонних скриптах.
* Комментарии в коде обещают «saved / duplicate / error», а фактически ещё есть
  `⏳ В работе`/`✅ Закрыт` в колонке «Статус» акта — это статусы строки, не записи.
